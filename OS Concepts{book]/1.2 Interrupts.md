# 1.2.1 Interrupts

## Why Interrupts Are Needed
- In I/O, the CPU/device driver starts an operation and cannot keep waiting actively.
- The device controller notifies completion or status using an interrupt.
- Typical status examples:
	- Read completed (data available)
	- Write completed successfully
	- Device busy / error

## Interrupt-Driven I/O (High-Level Sequence)
1. Device driver programs controller registers (operation details).
2. Controller performs data transfer between device and local buffer.
3. On completion/error/readiness, controller raises an interrupt.
4. CPU handles interrupt via interrupt service routine (ISR).
5. Driver/OS returns data or status and continues normal execution.

---

## 1.2.1.1 Overview

## Basic Idea
- Hardware can interrupt CPU asynchronously via system bus signal.
- CPU immediately pauses current execution and jumps to a fixed location.
- That location leads to the ISR start address.
- After ISR completes, CPU resumes interrupted work.

## Fast Dispatch Requirement
- Interrupts are frequent, so handling must be fast.
- Slow approach (generic handler that checks all sources) is inefficient.
- Fast approach: interrupt vector.

## Interrupt Vector
- Interrupt vector = array/table of ISR addresses.
- Interrupt request includes a unique interrupt number.
- CPU indexes vector with this number to jump directly to correct ISR.
- Usually stored in low memory in classical designs.
- Used by major OS families (for example, Windows and UNIX-like systems).

## State Save and Restore
- Before ISR changes CPU state (registers, etc.), state must be saved.
- ISR services event/device, then restores prior state.
- Return-from-interrupt reloads saved return address into program counter.
- Program continues as if interruption had not occurred.

## 1.2.1.2 Implementation

## Hardware Mechanism
- CPU has interrupt-request line(s), checked after each instruction.
- Controller asserts line to raise interrupt.
- CPU catches interrupt, reads interrupt number, dispatches via vector.

## Interrupt Handler Lifecycle
1. Save needed processor state.
2. Identify exact interrupt cause.
3. Perform service (read/write/error handling, acknowledgments).
4. Restore saved state.
5. Execute return-from-interrupt instruction.

## Terminology
- Controller raises interrupt (asserts request line).
- CPU catches and dispatches interrupt.
- Handler clears interrupt by servicing source.

## Why Advanced Interrupt Support Is Needed
- Modern OS requires more than basic mechanism:
	1. Defer interrupts during critical sections.
	2. Efficiently dispatch to correct device handler.
	3. Support multilevel priorities (urgent first).

## Maskable vs Nonmaskable Interrupts
- Nonmaskable interrupt (NMI):
	- Cannot be disabled.
	- Used for severe events (for example, unrecoverable memory errors).
- Maskable interrupt:
	- Can be temporarily disabled by CPU.
	- Used by device controllers for normal service requests.

## Interrupt Chaining
- Problem: number of devices can exceed vector slots.
- Solution: each vector entry points to a list (chain) of handlers.
- Handlers are tried in order until one claims/services the interrupt.
- Trade-off:
	- Smaller table than one huge direct table.
	- Faster than a single global handler scanning everything.

## Interrupt Priorities
- Hardware/OS assigns priority levels to interrupts.
- Benefits:
	- Defer low-priority work when needed.
	- Allow high-priority interrupts to preempt low-priority handlers.
	- Improve responsiveness for urgent events.

## Intel Event-Vector Snapshot (From Figure)
- Vector `0–31`: mostly nonmaskable/CPU exception-style events
	- Examples: divide error, debug exception, invalid opcode, page fault, machine check
- Vector `32–255`: maskable interrupts
	- Commonly used for device-generated interrupts

## Key Takeaways
- Interrupts are central to asynchronous event handling in OS.
- Efficient dispatch and low overhead are critical for performance.
- Priority + masking + proper state save/restore make interrupt handling safe and scalable.
