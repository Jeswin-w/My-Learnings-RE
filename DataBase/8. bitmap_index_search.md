# Bitmap Index Scan (PostgreSQL)

In PostgreSQL the planner chooses between index scans and sequential scans based on selectivity (how many rows match a condition). For example, on a table with 5 million rows:

- `SELECT * FROM table WHERE id < 100;` — only about 100 rows match, so an index scan is typically used.
- `SELECT * FROM table WHERE id > 100;` — if the condition matches a large fraction of the table, the planner may prefer a sequential scan.

A bitmap index scan is a hybrid strategy used when the planner expects a moderate number of matching rows or when combining multiple index conditions. The typical flow is:

1. Use one or more indexes to populate an in-memory bitmap. Each bit represents a heap page that contains at least one matching tuple.
2. If multiple index conditions are present, PostgreSQL builds multiple bitmaps and combines them with bitwise operations (AND / OR) to compute the final set of pages to read.
3. Perform a bitmap heap scan: read the selected heap pages in physical order and fetch matching tuples. Reading pages in order reduces random I/O compared to many separate index lookups.

Notes:
- Bitmap index scans reduce random page reads by grouping page accesses.
- They use temporary memory to store the bitmap; very large bitmaps may spill to disk or be expensive.
- The heap scan still needs to recheck index qualifications and tuple visibility when returning results.

This strategy is especially useful when combining conditions from multiple indexes or when the number of matching rows is neither very small nor a large fraction of the table.
