# Effective Java — Minimize Mutability

## 1. What is an Immutable Class?

An **immutable class** is a class whose objects cannot be modified after they are created.

Once an object is constructed, its state remains unchanged throughout its lifetime.

**Example:**

```java
String name = "Java";
name = name.concat(" Programming");
```

The original `String` object is not modified. `concat()` creates a new `String` object, and `name` refers to the new object.

Other examples of immutable classes in Java include `Integer`, `Long`, `BigInteger`, and `BigDecimal`.

## 2. Advantages of Immutability

1. **Easy to design and reason about** — an object's state cannot unexpectedly change.
2. **Thread-safe by design** — immutable objects can be shared between threads without synchronization, provided their construction and referenced state are also safe.
3. **Safe to share** — there is no need to create defensive copies when sharing the object.
4. **Useful for caching** — frequently used immutable objects can be cached and reused.
5. **Good building blocks** — immutable objects can be safely used as keys in hash-based collections, such as `HashMap`.
6. **No synchronization required for state changes** — because the object's state never changes after construction.

## 3. Disadvantages of Immutability

### Performance overhead

Creating a new object for every small change can be expensive, especially when the object contains large amounts of data or an operation requires many intermediate objects.

**Example:**

```java
String result = "";

for (int i = 0; i < 1000; i++) {
    result += i;
}
```

Since `String` is immutable, each concatenation creates a new string. This can result in unnecessary object creation.

**Solution: Use a mutable companion class.**

```java
StringBuilder result = new StringBuilder();

for (int i = 0; i < 1000; i++) {
    result.append(i);
}

String output = result.toString();
```

`StringBuilder` allows modifications without creating a new object for every append operation.

Other approaches include:

* Using primitive types for intermediate calculations when appropriate.
* Using mutable helper objects internally, while exposing an immutable public API.
* Using builders for constructing complex immutable objects.

## 4. Five Rules for Creating Immutable Classes

### Rule 1: Do not provide methods that modify the object's state

Avoid setters and other methods that change instance fields.

```java
// Mutable
class User {
    private String name;

    public void setName(String name) {
        this.name = name;
    }
}
```

An immutable version:

```java
final class User {
    private final String name;

    public User(String name) {
        this.name = name;
    }

    public String getName() {
        return name;
    }
}
```

The `name` field cannot be reassigned after construction.

### Rule 2: Prevent subclassing

Make the class `final` so that subclasses cannot introduce mutable behavior or override methods in ways that compromise immutability.

```java
public final class User {
    // Implementation
}
```

Alternatively, a class with only private constructors can prevent external subclassing, while a static factory method can control object creation.

```java
public final class User {
    private User() {
    }

    public static User create() {
        return new User();
    }
}
```

**Note:** Making a class `final` is generally the simplest approach when designing an immutable class.

### Rule 3: Make all fields `final`

A `final` field can be assigned only once.

```java
private final int age;
```

For primitive fields, this prevents reassignment after initialization.

However, `final` does not make a referenced object immutable.

```java
private final List<String> names = new ArrayList<>();

public void addName(String name) {
    names.add(name); // Still allowed
}
```

The reference cannot be reassigned, but the list itself can still be modified.

### Rule 4: Make all fields `private`

Private fields prevent callers from directly accessing and modifying the object's internal state.

```java
private final int age;
```

Avoid exposing mutable fields directly, even if the reference is `final`.

### Rule 5: Use defensive copies for mutable objects

If a class contains mutable objects, do not expose the internal objects directly.

Create defensive copies:

* When accepting mutable objects through a constructor.
* When returning mutable objects through getters.

**Example:**

```java
import java.util.Date;

public final class Employee {
    private final Date joiningDate;

    public Employee(Date joiningDate) {
        this.joiningDate = new Date(joiningDate.getTime());
    }

    public Date getJoiningDate() {
        return new Date(joiningDate.getTime());
    }
}
```

Without defensive copies, a caller could modify the employee's internal date:

```java
Date date = employee.getJoiningDate();
date.setTime(0);
```

With defensive copying, modifying the returned `Date` does not affect the `Employee` object.

**Important:** A shallow copy may not be sufficient if the object contains other mutable objects. Ensure that all mutable state is protected.

## 5. What if a Class Cannot Be Immutable?

If a class cannot be made immutable, **minimize its mutability**.

* Keep fields private.
* Expose only the methods that are necessary to modify state.
* Avoid unnecessary setters.
* Keep mutable state confined to a small part of the class.
* Prefer immutable objects for fields wherever possible.
* Avoid exposing internal mutable objects.

## Key Takeaways

* Immutable objects cannot change after construction.
* Immutability simplifies concurrency and makes objects safer to share.
* `final` prevents reassignment of a reference; it does not make the referenced object immutable.
* Use defensive copies for mutable inputs and outputs.
* Prefer immutable classes, but use mutable helper objects when performance requires them.
* If a class cannot be immutable, minimize the ways its state can change.

**Remember:** An immutable class must protect its entire observable state, not just prevent reassignment of its fields.
