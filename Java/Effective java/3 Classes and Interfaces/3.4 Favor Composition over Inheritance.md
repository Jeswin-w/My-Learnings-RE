# Effective Java — Favor Composition Over Inheritance

## 1. Inheritance: Use Only for True Subtyping

**Class B should extend class A only if B is genuinely a subtype of A.**

In other words, ask yourself:

> Is B really an A?

Inheritance represents an **IS-A relationship**, not merely a way to reuse code.

For example:

```java
class Animal {
    void eat() {
        System.out.println("Eating");
    }
}

class Dog extends Animal {
    void bark() {
        System.out.println("Barking");
    }
}
```

A `Dog` is an `Animal`, so inheritance makes sense.

However, if a class only needs to reuse some functionality from another class, composition is often more appropriate.

## 2. Problems with Inheritance

Inheritance can introduce tight coupling between a subclass and its superclass.

### Problem 1: Overriding Existing Methods

Suppose you want to extend the functionality of a method in the superclass.

```java
class InstrumentedHashSet<E> extends HashSet<E> {
    private int addCount = 0;

    @Override
    public boolean add(E element) {
        addCount++;
        return super.add(element);
    }

    @Override
    public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return super.addAll(c);
    }
}
```

At first glance, this implementation looks reasonable.

However, `HashSet` implements `addAll()` in terms of `add()`. Therefore, calling `addAll()` also invokes the overridden `add()` method.

As a result, the elements may be counted twice.

For example, adding three elements using `addAll()` could increase `addCount` by six instead of three.

This illustrates a key problem with inheritance:

**The subclass depends on the internal implementation details of the superclass.**

A change in the superclass's implementation can break the subclass, even if the superclass's public API remains unchanged.

### Problem 2: Changes in the Superclass Can Break the Subclass

A superclass may change its implementation or introduce new behavior in a future version.

The subclass may then:

* Produce incorrect results.
* Violate its own invariants.
* Become incompatible with the updated superclass.
* Require changes even though its own requirements have not changed.

Inheritance creates a dependency on the superclass's behavior, not just its interface.

### Problem 3: Method Name and Signature Conflicts

Suppose a subclass introduces a new method that does not exist in the superclass.

```java
class Parent {
    // Existing functionality
}

class Child extends Parent {
    public void processData() {
        // Additional functionality
    }
}
```

This is initially safe.

However, if a future version of `Parent` introduces a method with the same name and signature, the subclass method may become an override.

This can cause:

* Unexpected behavior.
* Compilation errors, especially if the new superclass method has an incompatible return type or access level.
* Violations of the subclass's intended behavior.

**Note:** Adding a method with the same signature does not always cause a compilation error. The outcome depends on the method declarations and Java's overriding rules.

## 3. Prefer Composition Over Inheritance

Instead of extending an existing class, create a new class that contains an instance of the existing class as a private field.

This is called **composition**.

The new class delegates the required operations to the contained object and can add its own functionality.

```java
class InstrumentedSet<E> implements Set<E> {
    private final Set<E> set;
    private int addCount = 0;

    public InstrumentedSet(Set<E> set) {
        this.set = set;
    }

    @Override
    public boolean add(E element) {
        addCount++;
        return set.add(element);
    }

    @Override
    public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return set.addAll(c);
    }

    public int getAddCount() {
        return addCount;
    }

    // Delegate the remaining Set methods to set.
}
```

Here, `InstrumentedSet` does not inherit the implementation of `HashSet`. Instead, it wraps a `Set` and delegates operations to it.

The counting logic is applied exactly once for each public operation in this example, without relying on how the underlying set implements `addAll()`.

## 4. Forwarding Classes

A **forwarding class** is a class that forwards method calls to another object.

It is commonly used to implement composition without duplicating the underlying implementation.

```java
class ForwardingSet<E> implements Set<E> {
    private final Set<E> set;

    public ForwardingSet(Set<E> set) {
        this.set = set;
    }

    @Override
    public boolean add(E element) {
        return set.add(element);
    }

    @Override
    public boolean addAll(Collection<? extends E> c) {
        return set.addAll(c);
    }

    // Forward all remaining Set methods.
}
```

Now, the instrumented class can extend the forwarding class:

```java
class InstrumentedSet<E> extends ForwardingSet<E> {
    private int addCount = 0;

    public InstrumentedSet(Set<E> set) {
        super(set);
    }

    @Override
    public boolean add(E element) {
        addCount++;
        return super.add(element);
    }

    @Override
    public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return super.addAll(c);
    }

    public int getAddCount() {
        return addCount;
    }
}
```

The forwarding class delegates operations to the contained `Set`, while `InstrumentedSet` adds counting behavior.

This approach is known as the **Decorator Pattern** when the wrapper adds responsibilities to an object while preserving its interface.

## 5. Advantages of Composition

* **Loose coupling:** The wrapper depends on the public interface rather than the implementation details of a superclass.
* **Safer extension:** Additional behavior can be introduced without overriding the superclass's implementation.
* **Reduced fragility:** Changes to the wrapped implementation are less likely to break the wrapper, provided its contract remains compatible.
* **Flexibility:** The wrapped object can be supplied through a constructor.
* **Reusability:** The same forwarding class can support different implementations of the interface.

## Key Takeaways

* Inherit only when a genuine IS-A relationship exists.
* Do not use inheritance solely to reuse code.
* Overriding methods can make subclasses fragile because they depend on superclass behavior.
* Adding methods to a subclass can create conflicts with future superclass changes.
* Prefer composition: store the existing object in a private field and delegate calls to it.
* Use forwarding classes to reduce delegation boilerplate.
* Use the Decorator Pattern when you need to add behavior while preserving an object's interface.

**Remember:** Inheritance exposes you to the superclass's implementation and evolution. Composition lets you reuse functionality while maintaining a clearer boundary.

## 6. Why Use a Forwarding Class Instead of Direct Composition?

A class can use composition directly by storing an instance of the required type in a private field.

```java
class InstrumentedSet<E> implements Set<E> {
    private final Set<E> set;

    public InstrumentedSet(Set<E> set) {
        this.set = set;
    }

    // Implement and delegate all Set methods
}
```

However, `Set` contains many methods. Even if `InstrumentedSet` only needs to add functionality to `add()` and `addAll()`, it must still implement the remaining methods and delegate them to the contained `Set`.

This results in repetitive boilerplate code.

### Solution: Use a Forwarding Class

A forwarding class implements the interface and delegates its methods to a contained object.

```java
class ForwardingSet<E> implements Set<E> {
    private final Set<E> set;

    public ForwardingSet(Set<E> set) {
        this.set = set;
    }

    @Override
    public boolean add(E e) {
        return set.add(e);
    }

    @Override
    public boolean addAll(Collection<? extends E> c) {
        return set.addAll(c);
    }

    // Delegate all remaining Set methods
}
```

Now, `InstrumentedSet` can extend `ForwardingSet`:

```java
class InstrumentedSet<E> extends ForwardingSet<E> {
    private int addCount = 0;

    public InstrumentedSet(Set<E> set) {
        super(set);
    }

    @Override
    public boolean add(E e) {
        addCount++;
        return super.add(e);
    }

    @Override
    public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return super.addAll(c);
    }
}
```

### Why Is Inheritance Used Here?

`InstrumentedSet` extends `ForwardingSet` to **reuse the delegation code**, not to inherit the underlying set's implementation.

* `ForwardingSet` contains the actual `Set` object as a private field.
* `ForwardingSet` delegates method calls to that object.
* `InstrumentedSet` overrides only the methods that require additional behavior.
* The underlying implementation can be a `HashSet`, `TreeSet`, or another `Set` implementation.

Therefore, this design still uses composition to reuse the underlying set's functionality.

### Comparison

| Direct composition                | Composition with a forwarding class                    |
| --------------------------------- | ------------------------------------------------------ |
| Stores a `Set` in a private field | Stores a `Set` in a private field                      |
| Implements `Set` directly         | Inherits the forwarding implementation of `Set`        |
| Must delegate every method        | Delegation is implemented once in the forwarding class |
| More repetitive code              | Less repetitive code                                   |

**Key takeaway:** A forwarding class is optional. Direct composition works perfectly well, but a forwarding class reduces boilerplate when wrapping an interface with many methods.

The inheritance here is between `InstrumentedSet` and `ForwardingSet` to reuse delegation code. The relationship with the actual `Set` implementation is still composition.
